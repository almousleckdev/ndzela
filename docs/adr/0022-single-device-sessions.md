# ADR-0022: Single-device sessions, DB-compared per request

**Status:** Accepted · **Date:** 2026-10-18

**Context.** Every account type (staff and drivers) could be signed in on any number of devices at once: each login issued its own independent access/refresh token pair, and nothing linked them. The platform needs to restrict every account, in every role, to one active device at a time, enforced server-side, consistently with the existing tenancy and lockout rules.

**Decision.**
- **One session id per account.** `users` and `drivers` each gain a nullable `session_id` column (`VARCHAR(64)`, an opaque `SecureRandom` string generated the same way `OpaqueTokens.generate()` already generates refresh tokens — never a predictable shape). A successful login overwrites it.
- **The access token carries it.** Both the staff and the driver access token gain a `sid` claim holding the session id that was current at issuance. `JwtService` already signs and verifies these tokens; adding one more claim does not change the trust model.
- **Checked on every request, like account status already is.** `JwtAuthenticationFilter` and `DriverJwtAuthenticationFilter` already re-read the account from the database on every request so a `DISABLED`/`LOCKED` account is rejected immediately (documented in `docs/auth/authentication.md`). The session check is additive to that same read: if the token's `sid` does not match the account's current `session_id`, the request is rejected exactly like a disabled account is today — no new filter, no new infrastructure.
- **Revocation timing is asymmetric, and that is accepted.** The old refresh token is revoked immediately (`RefreshTokenService.revokeAll`, the same call already used for every other account-state change — password change, disable, lock, MFA reset). The old *access* token has no server-side revocation list; it dies the way every other staff/driver access token already dies mid-session today (role changes, disables, etc. all rely on the same per-request DB read) — on its next validated request, worst case within its remaining TTL (15 minutes). This is a deliberate reuse of the existing trust model, not a new gap: it is exactly as "delayed" as every other instant account-state change already is.
- **No push-based kick.** The old device is not notified in real time; it simply gets `401` on its next action, through the existing session-expired path, the next time it touches the API.

**Consequences.** (+) One device at a time, enforced identically for staff and drivers, with no new moving parts — the same re-read-per-request pattern already in place. (+) An attacker who steals a valid access token loses it the moment the real owner logs in anywhere else. (-) The old device's own in-flight access token is not killed instantly; a narrow window (up to 15 minutes for staff, matching the existing access-token TTL) exists where the superseded token could still be used if an attacker already had it before the legitimate re-login — identical in shape to the existing disable/lock-detection latency, which the platform already accepts. (-) One more column per account type to keep populated correctly; forgetting to stamp it on any future login path silently disables single-device enforcement for that path (mitigated by the automated tests in this plan covering both login paths).

**Alternatives considered.** A Redis-backed access-token blocklist checked per request (rejected for this iteration: strictly tighter, closing the TTL window entirely, but adds a second source of truth to keep consistent with the refresh-token store; the existing TTL-bounded latency is accepted as consistent with how every other instant account-state change already behaves). A push/websocket "kicked" notification to the old device (rejected: no existing push channel to staff or driver clients, and out of scope for this plan). A per-device token list instead of single-device replacement (rejected: not what was asked — the requirement is exactly one device, not many tracked devices).
