# API conventions

Base path: **`/api/v1`**. JSON in and out (`application/json`), except uploads (`multipart/form-data`): the profile picture (max 2 MB, PNG/JPEG/WebP) and the driver files (max 5 MB, PNG/JPEG/WebP, PDF for documents; driver creation is one multipart request with a `data` JSON part).

Restrictive actions take a mandatory body `{ "reason": "..." }` (max 255): driver `suspend` (which also takes `releaseVehicle`, default false: frees the car and ends the contract) and `block` (frees the car), `POST /drivers/{id}/deactivate` frees it too, `POST /drivers/{id}/vehicle/remove`, user `disable` and `lock`; `POST /vehicles/{id}/status` takes `{ status, reason }` with the reason required except for `AVAILABLE` (`REASON_REQUIRED`, 422). **List parameters (2026-10-01):** every table list accepts `q` (search), `sort=field,asc|desc` against a whitelist per endpoint (an unknown field or direction answers `400 INVALID_PARAMETER`; the id is always the last tie-breaker) and `from` / `to` (inclusive whole days, `yyyy-MM-dd`, each country measured in its own timezone; either may be omitted) on the date that makes sense for the list: creation day for vehicles and drivers, `createdAt` for the ledger, recharges and audit, `lateFrom` / `lateTo` (overdue since) and `paidFrom` / `paidTo` (money collected in the period, returned as `collected`) for `GET /payments/accounts`; `GET /payments/summary?from&to` adds `collectedRange`. The recharges list replaces its former `day` parameter with `from` / `to`.

Charging: `GET/POST /charging/recharges` (client `requestId`), `POST /charging/recharges/{id}/reverse`, `DELETE /charging/recharges/{id}` and `DELETE /charging/sessions/{id}` (body `{reason}`, `charging:delete`, super administrator and administrator only, ADR-0031; errors `SESSION_HAS_RECHARGES`, `ENTRY_NOT_A_RECHARGE`; the `method` of a new recharge is always `ZELLA_WALLET`), `GET /charging/summary`, `GET /charging/id-tags?status=SUGGESTED|LINKED|UNLINKED`, `POST /charging/id-tags/{id}/confirm`, `POST /charging/id-tags/{id}/unlink {reason}`, `POST /charging/id-tags/lookup` (all `charging:link`; a session answers `holder: {driverId, driverName, vehicleId, vehicle}` or null for a public customer, and `payment: {state, total, energyCost, vat, serviceFee, currency, method, breakdownEstimated, capped, freeCategory}` (whole units; `freeCategory` is `NDZELA_STAFF`, `OTHER` or `FREE_SUNDAY` when Zella gave the charge free, so the dashboard shows "Offert" and no payment to record, [ADR-0044](../adr/0044-free-staff-charges.md)) or null when Zella reported nothing; errors `DRIVER_ALREADY_LINKED`), `POST /charging/sessions/{id}/stop` (`charging:stop`, super administrator, administrator and manager, [ADR-0042](../adr/0042-stopping-a-charge-from-both-dashboards.md): asks the Zella app to stop the charge; 204, or 422 `SESSION_NOT_ACTIVE`, `STOP_REFUSED`, `ZELLA_UNAVAILABLE`; audited as `CHARGING_SESSION_STOP_REQUESTED`), `GET /charging/sessions/summary` (`today, yesterday, week, month`, each `{sessions, energyKwh, collected, staffEnergyKwh}`: the network sessions started in the period, their energy, what the drivers paid from the Zella wallet (state `CHARGED`, never a free charge) and the NDZela staff's energy, which is never collected; optional `chargePoint` and `driverId` narrow it to one charger or one driver; days run in the country's time zone and match Zella's console; `charging:read`), `/export?period=DAY|WEEK|MONTH|YEAR&date=`, `/vehicles`, and `/charging/stations`. `GET /charging/suspension-cases?page=&size=` (`arrears:manage`; [ADR-0033](../adr/0033-arrears-suspension-in-both-apps.md)): the attempts to help a suspended driver that the Zella app refused, newest first, each `{id, occurredAt, kind, amountMinor, currency, suspended: {id, name, vehicle}, helper: {id, name, vehicle} or null, helperReference, score, reasons, flagged}`; the helper is a driver only when that Zella account is also a linked NDZela driver (then `score` and, when `flagged`, `reasons` come from OVERLAP, BATTERY_CHAIN, ENERGY), otherwise only the irreversible `helperReference` and `score` null. `GET /charging/suspension-cases/patterns` (`arrears:manage`): while at least one driver is suspended for arrears, the linked accounts whose last 7 days of charges score 60 or more (`{account: {id, name, vehicle}, score, reasons, suspendedDrivers}`, at most 50, highest first); nothing links such an account to one suspended driver, so it is a hint for staff only. `GET /charging/sessions` (the network's sessions, `charging:read`, served by the charging module) answers each session with `durationSeconds, pricePerKwh, powerKw` (only while it runs), `socBefore` / `socAfter` and `rechargeId` (the recharge that recorded its payment, null while unpaid). `POST /charging/recharges` takes an optional `sessionId`: the session must exist in the caller's country (404 otherwise), be finished (`SESSION_NOT_FINISHED`) and not already paid (`SESSION_ALREADY_RECORDED`); cancelling the recharge frees it. A recharge answers `sessionId`. Errors `CHARGING_TARGET_INVALID`, `VEHICLE_HAS_NO_DRIVER`, `BATTERY_LEVELS_INVALID`, `STATION_NAME_TAKEN`, `STATION_IN_USE`.

Payments: `GET /payments/accounts`, `/accounts/{driverId}` (also `weekClosesAt`, `weekSettled`), `/summary`, `/history` (`scope=CURRENT|FORMER|ALL`; each entry lists the `days` it settled), `/export`, `GET /payments/{id}/receipt` (`payments:read`: the ticket receipt PDF of a recorded payment, by ledger entry id or app attempt id); `POST /payments` (body includes a client `requestId` for idempotency), `POST /payments/{id}/reverse`, `POST /arrears/waivers`; `GET /drivers?late=`. **Rent is paid with the country's mobile-money operators only (2026-10-02):** `GET /payments/operators` (`payments:read`) lists them (Gabon Airtel and Moov, Mali Orange and Moov); `POST /payments` refuses any other method (`PAYMENT_METHOD_NOT_ALLOWED`) and always needs the operator's transaction number as `reference`; payments confirmed by PVit are recorded by `PVit (automatique)`. Each row of `GET /payments/accounts` also carries `paidDays, unpaidDays, elapsedDays, totalDays, daysLeft`, and `GET /drivers` answers `arrears.unpaidDays, paidDays, daysLeft`. Day incidents (permission `arrears:manage` to declare or cancel, `payments:read` to list): `GET /drivers/{id}/incidents`, `POST /drivers/{id}/incidents {day, kind: HALF_DAY|STOP, cause: ELECTRICITY|OTHER, hours (1-24), note}` and `POST /drivers/{id}/incidents/{incidentId}/cancel`; errors `DAY_OUT_OF_CONTRACT`, `DAY_NOT_BILLABLE`, `INCIDENT_HOURS_INVALID`, `INCIDENT_NOTE_REQUIRED`, `INCIDENT_ALREADY_DECLARED`, `INCIDENT_NOT_LIVE`, `NO_ACTIVE_CONTRACT`. `POST /auth/forgot-password` and `POST /driver/auth/forgot-password` are limited per address (`422 TOO_MANY_REQUESTS`); the staff one also silently sends nothing once an account has received its hourly quota, so the answer never changes. A transaction reference (per operator, case and spaces ignored) can be recorded once while its payment is not reversed (`PAYMENT_REFERENCE_ALREADY_USED`, 422). Errors `PAYMENT_REFERENCE_REQUIRED`, `PAYMENT_REFERENCE_ALREADY_USED`, `NO_ACTIVE_CONTRACT`, `ENTRY_ALREADY_REVERSED`, `ENTRY_NOT_REVERSIBLE`.

Deletion: `DELETE /drivers/{id}` and `DELETE /vehicles/{id}` erase the record with its contracts and assignments only while no payment or recharge exists; errors `DRIVER_HAS_HISTORY`, `VEHICLE_HAS_HISTORY`, `VEHICLE_ASSIGNED` (all 422).

Purge: `POST /drivers/{id}/purge {confirm: true}` (`drivers:purge`, 204; `confirm` false or missing is a 400; error `DRIVER_PURGE_BLOCKED`). Half days and stops: declaring and cancelling need `incidents:declare`; the day may be today or up to 7 days ahead, cause `LATE_SIGNING` (half day only; `INCIDENT_KIND_INVALID` otherwise), see [ADR-0035](../adr/0035-purging-a-driver-with-their-money-and-half-days-for-today.md). Contract update: `PUT /drivers/{id}/contract {deposit}` (`contracts:update`), error `CONTRACT_NOT_ACTIVE`; contract responses carry `revision` and `updatedAt`. Change of car on the same contract: `PUT /drivers/{id}/vehicle {vehicleId}` (`drivers:update` and `contracts:update`; errors `VEHICLE_NOT_AVAILABLE`, `VEHICLE_UNCHANGED`, `DRIVER_HAS_NO_VEHICLE`, `NO_ACTIVE_CONTRACT`). Start date: `PUT /drivers/{id}/contract/start-date {startDate}` (`contracts:update`; errors `START_DATE_OUT_OF_RANGE`, `CONTRACT_HAS_ACTIVITY`, `NO_ACTIVE_CONTRACT`), see [ADR-0034](../adr/0034-change-car-and-start-date-on-an-active-contract.md).

Contracts: `GET /contracts?driverId=`, `GET /contracts/{id}`, `GET /contracts/{id}/pdf` (`application/pdf`, audited), `POST /contracts/preview`; errors `CONTRACT_TEMPLATE_UNAVAILABLE`, `CONTRACT_ALREADY_ACTIVE`, `DEPOSIT_INVALID`. `POST /drivers` now requires `vehicleId` and `contract.deposit`; `POST /drivers/{id}/vehicle` requires `deposit`.

Rescheduled rent days: `GET`/`POST /payments/accounts/{driverId}/rescheduled-days`, `DELETE .../{id}` (`payments:reschedule_days`, ADR-0047). Taking the car and keeping the contract: `POST /drivers/{id}/vehicle/release {reason}` (`drivers:update`); `POST /drivers/{id}/vehicle` continues a contract that has no car.

Cancelled rent days: `GET`/`POST /payments/accounts/{driverId}/cancelled-days`, `DELETE .../{id}` (`payments:cancel_days`, [ADR-0043](../adr/0043-cancelled-rent-days.md)).

Drivers: `GET /drivers/stats` (replaces `/counts`), `GET /drivers?status=&onLeave=&scope=CURRENT|FORMER|ARCHIVED&q=`, `GET /drivers/export`, `POST /drivers/{id}/deactivate`, `POST /drivers/{id}/archive {reason}` (`drivers:archive`; `CONTRACT_HAS_ARREARS` while rent is late), `POST /drivers/{id}/unlock-login` (`drivers:unlock`; clears a login-attempt lockout, no body, never touches `status`/suspend/block — `GET`/`POST /drivers/{id}` answers `loginLocked`), leaves under `/drivers/{id}/leaves`. Leave errors: `LEAVE_IN_PAST`, `LEAVE_DATES_INVALID`, `LEAVE_TOO_LONG`, `LEAVE_NOTE_REQUIRED`, `LEAVE_OVERLAP`, `LEAVE_STARTED`; `DRIVER_NOT_ACTIVE`. Exports are an Excel file or a PDF, chosen with `format=XLSX|PDF` (default `XLSX`, anything else is a 400), max 10 000 rows, audited ([ADR-0020](../adr/0020-table-exports-as-excel-or-pdf.md)): `GET /drivers/export`, `GET /vehicles/export`, `GET /payments/export` (ledger transactions, the Transactions tab), `GET /payments/accounts/export` (`payments:export`; the driver-balance view behind `/finance/payments`, `/finance/arrears` and the Progression tab of `/finance/history` — same filters as `GET /payments/accounts`, no `/payments/export`), `GET /charging/export` (the manual recharges), `GET /charging/sessions/export` (the network's sessions; `GET /charging/sessions`, `/sessions/summary` and `/sessions/export` take `kind=ALL|DRIVER|PUBLIC`, default `ALL`, an unknown value is a 400; [ADR-0028](../adr/0028-public-sessions-from-the-zella-feed.md)), `GET /users/export` (`users:export`, no filters) and `GET /audit/export` (`audit:export`, same filters as `GET /audit`); they all take the dates (`from`, `to`) and search of the page they come from, where that page has any. The file name comes from `Content-Disposition`. Numbers and dates stay typed in Excel; text starting with `=` stays text.

File errors: `INVALID_FILE`, `FILE_TOO_LARGE`, `PHOTO_REQUIRED`; a blocked driver: `DRIVER_BLOCKED`.

Vehicle photos (Implemented): one or more private images per vehicle, added after the vehicle exists (vehicle creation itself stays plain JSON). `GET /vehicles/{id}/images` (`vehicles:read`) lists them; `POST /vehicles/{id}/images` (`vehicles:update`, multipart, one or more `files` parts) adds photos and answers the full updated list; `GET /vehicles/{id}/images/{imageId}` (`vehicles:read`) serves one as an image; `DELETE /vehicles/{id}/images/{imageId}` (`vehicles:update`) removes it. At most 8 photos per vehicle (`TOO_MANY_IMAGES`, 422); same 5 MB/PNG-JPEG-WebP rules as other images (`INVALID_FILE`, `FILE_TOO_LARGE`).

Driver app API (Implemented, [ADR-0013](../adr/0013-driver-api-token-audience-and-login-lookup.md)), all under `/api/v1/driver`, driver tokens only: `POST /auth/login {identifier, password}` (email or phone) and `POST /auth/refresh {refreshToken}` answer `{accessToken, refreshToken, expiresIn, mustChangePassword}` (refresh token in the body, no cookie); `POST /auth/forgot-password {identifier}` (202, public; always the same answer, a 6-digit code is e-mailed when the account exists and has an e-mail; one code per cooldown) `POST /auth/verify-reset-code {identifier, code}` (204, public; checks the code without using it so the app can show the new-password screen only for a good code; `INVALID_RESET_CODE` otherwise; every check counts as one of the 3 tries) and `POST /auth/reset-password {identifier, code, newPassword}` (204, public; `INVALID_RESET_CODE` for a wrong, expired or over-tried code; ends every session, lifts a lock; same OTP rules as staff: 3 minutes, 3 tries); `POST /auth/logout {refreshToken}` (204); a refresh refused because a newer sign-in replaced the session answers `401 SESSION_REPLACED`, any other refusal `401 SESSION_EXPIRED` ([ADR-0027](../adr/0027-refresh-token-reuse-window.md)); `PUT /me/password {currentPassword, newPassword}` (min 8, returns new tokens; the only call allowed while `mustChangePassword`); `GET /me` (`firstName, lastName, phone, localPhone, email, birthDate, address, countryCode`; the app colours itself orange for GA and green for ML), `GET /me/photo` (the driver's own picture as an image, 404 when none, never cached), `PUT /me/photo` (multipart `file`, an image up to 5 MB, 204; the driver sets or replaces their own picture, audited `DRIVER_FILE_UPDATED`), `GET /vehicle` (`brand, model, plate`, ACTIVE drivers only), `GET /contract` (`contractNumber, startDate, endDate, durationMonths, dailyRent, currency`, ACTIVE drivers only), `GET /documents` (`[{kind: CONTRACT|LICENCE|ID|ADDRESS_PROOF, available}]`), `GET /support` (`phone, whatsapp, email` of the driver's country, a channel not set is null), `POST /support/messages {message}` (201, max 1000 characters, 5 per hour per driver, alerts the staff holding `drivers:update` in that country as a `DRIVER_MESSAGE` notification), `POST /account/deletion-request` (201, no body: stored as a support message, audited `DRIVER_DELETION_REQUESTED`, and a `DRIVER_DELETION_REQUEST` notification to the staff holding `drivers:update`; required by the store policies, the staff decide what the law lets them erase), `GET /account` (`unpaidDays, totalDue, currency` in whole units, `options: [{days, amount}]` the numbers of days that can be paid, `weekClosesAt` and `weekSettled` (the week's rents are due by Sunday noon), `days: [{day, amount, status: PAID_ON_TIME|PAID_LATE|UNPAID|AWAITING, paidAt}]` (the rent days of the last 4 weeks, oldest first; `AWAITING` = the day ended and its deadline has not come), `locked`: three or more unpaid days, only the payment screen is allowed until all is paid; `suspended`: only an administrator can lift it), `GET /payments/operators` (`[{code, label}]` of the driver's country). Errors `INVALID_CREDENTIALS` (401), `ACCOUNT_LOCKED` (423), `DRIVER_BLOCKED`, `PASSWORD_INCORRECT`, `PASSWORD_UNCHANGED`, `NO_ACTIVE_CONTRACT`, `TOO_MANY_MESSAGES` (422). Payments through PVit ([ADR-0014](../adr/0014-pvit-mobile-money-payments.md)): `GET /payments/quote?operator=&phone=&days=` (`{days, amount, fee, currency, accountHolder, options: [{days, amount}]}`), `POST /payments {operator, phoneNumber, days?}` (202, `{id, status: PENDING|SUCCESS|FAILED|EXPIRED, amount, fee, currency, operatorCode, phone, beneficiary, reference, providerReference, createdAt, completedAt, days: [{day, kind: RENT|PENALTY, amount, onTime}]}`; `days` omitted pays everything; with 1 or 2 unpaid days 1..N may be paid (oldest first), from 3 only all of them, else `INVALID_PAYMENT_DAYS` (422), see [ADR-0021](../adr/0021-day-based-rent-payments-and-receipts.md); `beneficiary` is the company of the driver's country that receives the money; the amount is never sent by the client), `GET /payments/{id}` (own attempts only, polled by the app every few seconds), `GET /payments/{id}/receipt` (the receipt of a confirmed payment as `application/pdf`, drawn by the server; `RECEIPT_NOT_AVAILABLE` (422) for any other status) and `GET /payments` (the last 50). Errors `NOTHING_TO_PAY`, `PAYMENT_IN_PROGRESS`, `OPERATOR_NOT_AVAILABLE`, `PHONE_INVALID` (422) and `PAYMENT_PROVIDER_UNAVAILABLE` (502). PVit's callback is `POST /api/callback` (public, rate-limited per address: 429 beyond `RATE_LIMIT_PVIT_CALLBACK` per minute, the recheck job settles what was refused; it does not decide anything, the answer is read back from PVit; the reply echoes `transactionId` and `code`). Staff: `GET /payments/transactions?status=&method=&q=&scope=&from=&to=&page=&size=` (`payments:read`; `scope=CURRENT|FORMER` separates archived riders; each row also carries `paidAt` and `days`, the rent days the payment settled) lists the payments of the caller's country (driver-app attempts, `source` PVIT, and payments entered by staff, `source` MANUAL; `status` SUCCESS, FAILED, PENDING, EXPIRED or REVERSED; the row id of a MANUAL payment is its ledger entry id). A confirmed payment adds a `PAYMENT` line to the ledger and, when the driver paid a fee on top, a `FEE` line of its own.

## Resources and verbs (Implemented pattern)

- Plural nouns: `/users`, `/roles`, `/notifications`. Standard verbs: `GET` list/read, `POST` create, `PUT` replace/update, `DELETE` remove.
- State transitions and actions are `POST /<resource>/{id}/<action>` (e.g. `/users/{id}/disable`, `/lock`, `/reset-mfa`). Keep actions as verbs of the *domain*.
- The current user's own data is under `/profile/me`, `/profile/password`, `/profile/picture`, `/profile/mfa/reset`.
- Auth endpoints (public) are under `/auth/**` (login, verify-otp, resend-otp, mfa/setup, verify-totp, refresh, logout, forgot-password, forgot-password/reset, reset-password).
  `forgot-password` emails a 6-digit OTP code (not a link); `forgot-password/reset {email, code, newPassword}` consumes it (`INVALID_RESET_CODE`, 422; no account enumeration). `reset-password {token, newPassword}` stays link-based, for invitation redemption only.
  `POST /auth/login` and `POST /driver/auth/login` are also rate-limited per IP address, before the account lookup runs: `429 TOO_MANY_REQUESTS` beyond `RATE_LIMIT_LOGIN_PER_IP` attempts/minute (default 20) — distinct from the per-address/per-account `422 TOO_MANY_REQUESTS` on the forgot-password endpoints below.
- Success: `200` with body, `201` on create, `204` when there is no body.

## Authentication and authorization

`Authorization: Bearer <access token>` on everything except `/auth/**`. Each endpoint is guarded by `@PreAuthorize` on a permission
([authorization](../auth/authorization.md)). Country scope is applied server-side ([multi-tenancy](../multi-tenancy/multi-tenancy.md)).

## Headers

| Header | Direction | Purpose |
| --- | --- | --- |
| `X-Request-ID` | request/response | Correlation id. Generated if absent; echoed back; present in error bodies and logs. |
| `Authorization` | request | Bearer access token. |
| `X-Country` | request | The super admin's country filter (a country code such as `GA`); ignored for everyone else; absent means all countries. An unknown or inactive code answers `400 INVALID_COUNTRY`. |

CORS: allowed origins from `CORS_ALLOWED_ORIGINS`; allowed headers `Authorization, Content-Type, X-Request-ID, X-Country`; credentials allowed (refresh cookie).

Country error codes: `INVALID_COUNTRY` (400), `COUNTRY_REQUIRED` (422, a country must be selected), `COUNTRY_NOT_ALLOWED` (422, creating a user outside your own country), `COUNTRY_INACTIVE` (403, defensive: users of an inactive country are normally stopped earlier with 401 or 423).

## Error format (single shape, Implemented)

```json
{ "timestamp": "2026-09-30T14:50:45+01:00", "status": 401, "code": "INVALID_CREDENTIALS",
  "message": "Invalid email or password.", "path": "/api/v1/auth/login", "requestId": "…",
  "errors": [ { "field": "email", "message": "…" } ] }
```

`errors` is only present for `VALIDATION_ERROR` (400). Status mapping: 400 validation/malformed (a bad query parameter answers `INVALID_PARAMETER`), 401 unauthenticated/`SESSION_EXPIRED`, 403 forbidden, 404 not found,
405, 422 business rule (`code` identifies the rule), 423 account locked, 500 unexpected (generic message, details only in logs).
The `code` is the contract: clients branch on `code`, never on `message`. Messages are English and technical; the UI shows its own French text per `code`.

## DTO rules

- Java records under `<feature>/api/dto`; naming `...Request`, `...Response`, `...Summary`. Never expose entities. Never expose password hashes, MFA secrets, tokens.
- IDs are UUID strings; timestamps ISO-8601 with offset; enums as their string names; money as decimal strings or integer minor units with an explicit currency (decided per module).
- Requests validated with bean validation; unknown/extra fields are ignored; role names and codes are `UPPER_SNAKE_CASE`.

## Evolution

Additive changes (new optional fields, new endpoints) stay in `v1`. A breaking change needs `v2` (or a versioned resource) and an ADR. Lists that can grow are paginated
(**Implemented** for audit, vehicles and drivers: query `page` from 0 and `size` (default 20, max 100); response `{items, page, size, total}`). The older lists (`/users`, `/roles`) are still unpaginated and recorded in findings.
