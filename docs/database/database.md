# Database architecture

PostgreSQL 16 (dev: Docker on port 5433, database `ndzela_admin`). Access via Spring Data JPA/Hibernate. **The schema is owned by Flyway**
(`backend/src/main/resources/db/migration`); Hibernate runs with `ddl-auto: validate` and must never create or alter tables.

## Current schema (Implemented, migrations V1-V6)

| Table | Purpose | Notes |
| --- | --- | --- |
| `users` | Staff accounts | `email` unique; `status`; failed attempts and lock expiry; `mfa_secret` stored encrypted; profile fields (V2) |
| `roles`, `permissions`, `role_permissions`, `user_roles` | RBAC | UUID keys; role and permission `name` unique; `ON DELETE CASCADE` on the link tables |
| `notifications` | In-app notifications | `user_id` FK (cascade), `is_read`, index `(user_id, created_at DESC)` |
| `audit_logs` | Intended audit trail | Created in V1, **no entity and nothing writes to it** (see findings) |

Ephemeral auth data (challenges, OTP, refresh tokens, reset links) is in **Redis**, not in PostgreSQL.

## Conventions (binding for new tables)

- Primary keys: `UUID`. Generated by the application (`GenerationType.UUID`).
- Naming: `snake_case`, plural table names, `<singular>_id` foreign keys, `created_at`/`updated_at` as `TIMESTAMP WITH TIME ZONE` (always store instants in UTC, convert for display using the country's timezone).
- Every column has an explicit `NOT NULL` decision. Add FKs and the indexes the queries need (FK columns, `(country_id, ...)` for tenant lists).
- Enumerations are stored as `VARCHAR` matching a Java enum (`@Enumerated(STRING)`), never ordinal.
- **Tenant-owned tables** include `country_id UUID NOT NULL REFERENCES countries(id)` and an index starting with `country_id` ([multi-tenancy](../multi-tenancy/multi-tenancy.md)).
- **Money**: never floating point. Use `NUMERIC(19,4)` (or integer minor units) plus an explicit `currency` (ISO 4217, from the country). One rounding rule, defined once. Amounts are never negative unless the column is explicitly a signed ledger movement.
- **Ledgers are append-only**: corrections are new compensating rows, never updates or deletes of posted financial records.
- Soft delete vs hard delete is decided per module (financial and contract records: never hard-deleted).

## Flyway rules

1. Migrations are `V<n>__snake_case_description.sql`, numbered sequentially, **immutable once applied anywhere shared**. Fix mistakes with a new migration.
2. One logical change per migration. Destructive changes (drop/rename column or table) need a written rollout plan.
3. Seed data that is part of the platform (permissions, base roles) lives in migrations and is idempotent (`ON CONFLICT DO NOTHING`).
4. Data migrations that need business knowledge (e.g. assigning existing users to a country) require the user's decision first.
5. Test the migration on a copy of realistic data before merging. The app must start cleanly against an empty database and against the previous schema.

## Access patterns

- Repositories are per aggregate in `<feature>/domain`. Avoid `EAGER` associations on new entities; fetch explicitly.
- Paginate any list that can grow. Add indexes with the feature, not after the incident.
- No native SQL that bypasses the tenant filter without an ADR.

## Environments

Dev database credentials in `docker-compose.yml` are for local use only. Production credentials come from environment variables (`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`); never reuse dev defaults.
